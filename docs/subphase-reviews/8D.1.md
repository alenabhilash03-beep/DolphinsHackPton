# 8D.1 review — Typed next-experiment proposals

## Delivered

- **Proposals for every stored result**, derived by the server from solver facts: extend a window that cuts durations off, raise a threshold that does not separate scenarios, double a dose that never reaches the threshold, halve a dose that never drops below it.
- **Each proposal states** the solver observation, the question it tests, the rationale, the exact change with units and old and new values, and the base result, experiment, configuration hash and revision.
- **Run this experiment** in the workspace. Only the proposal ID is sent; the server re-derives the proposal from the stored base and applies it through the same validated controls as sliders and edits in words. The resulting turn records which proposal produced it.
- **Edit language as structured operations**, with two new forms (halve a dose, set the occupancy threshold). Whole-request matching, clarification on anything else, and the protected baseline are unchanged.
- **Workspace panel** under the answer, re-derived for whatever result is displayed, including after slider edits.

## Verification

- **408 backend tests (21 new) and 60 frontend tests (4 new) pass.** TypeScript, contract check and production build pass. The one failing backend test is the same pre-existing saved-demo float mismatch.
- **Required cases:**
  - proposal-to-config equality: running a proposal, typing its edit text and making the direct control change give the same configuration, metrics and curves;
  - stale bases: a proposal ID is refused on any other result, and a wrong hash or revision is rejected;
  - unsupported clauses: extra instructions, baseline edits, out-of-range thresholds and vague wording apply nothing;
  - unchanged parameters: only the listed parameter differs and the baseline scenario is identical;
  - new drug, target or model scope is never proposed.
- **Browser, synthetic backend:** the saved demo shows three proposals; running "Raise the occupancy threshold to 95%" completes with the attribution line; the new result has its own proposals; a slider edit re-derives them for the edited curves. No page errors, no overflow at 390 px.
- **Browser, live Nemotron:** the same run completed. The answer reports that at 95% the baseline and the stronger-affinity scenario cross within the window while the longer half-life scenario stays above it.

- Proposals are rule-based and few. They follow the solver, not the papers or the structure.
- The answer's model-written "What to test next" items are still qualitative and not runnable, so the workspace now has two lists of next steps with different status.
- Running a proposal consumes the base result's single edit slot, like any edit. Returning to an earlier result to try a different proposal needs 8D.2.
- For the reviewed comparison the 95% threshold proposal resolves the censoring that the answer could not: the scenarios separate.
